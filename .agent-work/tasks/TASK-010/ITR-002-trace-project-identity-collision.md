## Expected result

Identify where project identity becomes ambiguous, how existing candidate/task records are keyed, and whether source metadata is sufficient to safely distinguish the observed projects before adding project-workspace mutations in Angular.

## In scope

- Trace Boy Scout/MCP imports into Todo Graph request models.
- Trace project and task identity through Todo Graph schema, migrations, and project/task APIs.
- Inspect focused tests and report concrete gaps in the identity contract.

## Out of scope

- Changing persistent project identity or migrating existing rows before a safe mapping is established.
- Migrating the Angular project workspace or changing external API contracts in this discovery iteration.
- Inspecting local database files or directories outside the repository.

## Primary risk

Changing project identity may reassign existing worktrees, candidates, tasks, or raw submissions if old rows cannot be mapped unambiguously.

## Verification method

Code/schema/test trace and a concise mapping of each identity field and its scope; no production-data inspection.

## Findings

- Boy Scout project IDs are generated by each local Boy Scout database (`projects.id`); the same numeric value can occur in separate installations.
- `TodoGraphPublisher` currently sends `sourceProjectId` and the project path/name, but no namespace for the source database.
- `CandidateImport`, `ImportedTask`, `candidates`, `task_nodes`, and `project_repositories` key project membership/configuration on `source_project_id` alone. Imported task uniqueness is `(source_project_id, source_task_id)`.
- Candidate/task project paths remain stored in their `project` columns, so the observed ID `2` rows are distinguishable by labels/paths in the current API response. The running service currently returns both; the updated source query groups fallback rows by numeric ID and can hide one instead of resolving the collision.
- `BoyScoutReport.SourceInstallationId` is not a safe substitute for a source-database namespace: local reports set it from the local config, but Firebase-mapped reports preserve the remote note's originating installation ID while `ProjectId` is mapped in the current local database.
- The current project-specific routes and raw submission API accept only the numeric project ID, so Angular cannot safely disambiguate the two projects by itself.

## Decision required

The backend needs a stable project identity contract before project mutations are ported. Recommended: introduce an internal Todo Graph project ID and identify imported projects by `(source database installation ID, source project ID)`, explicitly separate from report-origin metadata. Keep project name/path as descriptive and migration-matching data; never silently merge ambiguous legacy rows. This requires adding the database namespace to Boy Scout publication and migrating project/repository/task/candidate references.

Alternative: key projects by `(source_project_id, project path/name)`. This avoids requiring a new source namespace but treats path changes/aliases as distinct projects and is not stable across relocated checkouts.

## Human direction

The user chose project identity “по id”. Interpret this as a unique internal Todo Graph project ID for UI, API, and task/repository references; do not reuse the colliding upstream numeric ID as the internal ID.

## Result

Identity collision source is traced. No persistent identity or API contract change has been made in this discovery iteration.

## Topic check

The project workspace migration depends on this finding because its list, raw submissions, task queries, and branch actions use a project identifier. Keep this iteration limited to establishing the identity contract; defer the migration design to a separate decision/implementation iteration if multiple safe options remain.
